# Интеграция БД (Supabase)

## 1. Зачем

Бот — прослойка перед основной системой. Раньше очищенный текст уходил
пользователю файлом `.md`, а сама система его не видела. Теперь финализация
записывает валидированный текст сессии в Supabase — основная система позже
возьмёт его оттуда и нарежет на чанки. Пользователь файл больше не получает:
ему приходит только отчёт, в котором виден статус записи в БД.

## 2. Где что лежит

```
supabase/schema.sql                  — SQL-схема (применяется вручную в SQL Editor)
src/shared/api/supabase.ts           — единственный клиент Supabase (ленивый синглтон)
src/entities/material/
  types.ts   — MaterialRecordInput, MaterialRecord, MaterialSaveResult
  api.ts     — saveMaterial(): insert в таблицу materials
  index.ts   — публичные экспорты сущности
src/features/finalize/index.ts       — сборка записи и вызов saveMaterial
src/features/report/index.ts         — секция «Запись в БД» отчёта
src/bot/lib/sink.ts                  — выдача: только отчёт, без файла
src/shared/config/env.ts             — DATABASE_URL, DATABASE_API_SUPABSE
```

Слои по FSD: `shared/api` — инфраструктура клиента, `entities/material` —
сущность «запись материала» с её API, `features/finalize` — оркестрация,
`bot/lib` — презентация.

## 3. Схема таблицы

Таблица `public.materials` — **одна строка на финализацию** (весь склеенный
текст сессии), не на отдельный материал:

| Колонка | Тип | Что содержит |
|---|---|---|
| `id` | uuid, PK | `gen_random_uuid()` |
| `created_at` | timestamptz | дата записи (по умолчанию `now()`) |
| `text` | text | валидированный текст сессии |
| `chars_before` | integer | символов до очистки (сумма по элементам) |
| `chars_after` | integer | символов после очистки |
| `items_count` | integer | сколько материалов в сессии |
| `audio_count` | integer | сколько голосовых/аудио |
| `audio_duration_sec` | integer | суммарная длительность аудио |
| `validation_ok` | boolean | итог валидатора по склеенному тексту |
| `warnings` | jsonb | предупреждения очистки (массив строк) |
| `stats` | jsonb | `CleanupStats`: срабатывания правил по категориям |

RLS включён, политик нет: `anon`/`authenticated` таблицу не видят вовсе,
запись идёт только service key (он RLS обходит). Service key живёт только
на сервере в env — в клиентский бандл не попадает.

## 4. Переменные окружения

| Переменная | Что это |
|---|---|
| `DATABASE_URL` | URL проекта Supabase (`https://xxxx.supabase.co`) |
| `DATABASE_API_SUPABSE` | Service role secret key из Supabase |

Обе обязательны: без них `getEnv()` падает с понятной ошибкой. Список —
в `.env.example`.

## 5. Поток данных

```
финализация (кнопка «Загрузить в систему» / /done)
  → cleanup + autofix каждого элемента (без изменений)
  → склейка в один текст + валидация целиком (без изменений)
  → saveMaterial(): одна строка в materials
       ├─ ok    → отчёт с секцией «Запись в БД: выполнена» → сессия очищается
       └─ error → отчёт с секцией «Запись в БД: не выполнена» → сессия СОХРАНЕНА,
                  бот просит повторить /done (очистка прогонится заново)
  → sink: только отчёт, файл .md не отправляется
```

Запись идёт **до** отправки отчёта, чтобы статус был честным. Ошибка БД не
роняет финализацию: отчёт всё равно уходит, а исход `db-failed` сохраняет
сессию для повтора.

## 6. Отчёт

Секция «Запись в БД»:

- успех: статус, ID записи, дата записи, сколько символов записано;
- сбой: статус «не выполнена» и причина (текст ошибки Supabase).

Секция «Подготовка к чанкованию» удалена — нарезка чанков в отчёте не
упоминается, это задача основной системы. Остальные секции (материалы с
«было → стало», что исправлено, аудио, валидация, автопочинка) без изменений.

## 7. Почему так

- **Одна строка на сессию.** Основная система режет на чанки цельный
  материал; отдельные элементы сессии — деталь приёма, а не хранения.
- **supabase-js, а не SQL-драйвер.** Insert через REST проще, клиент
  типизирован, отдельный коннект к Postgres не нужен.
- **Ошибки БД не бросаются.** `saveMaterial` возвращает `MaterialSaveResult`:
  финализация обязана показать отчёт даже при сбое, а сессия не теряется.
- **RLS без политик.** Проще и безопаснее, чем «политика только для service
  role»: публичный доступ закрыт полностью по умолчанию.

## 8. Как развернуть

1. В SQL Editor Supabase выполнить `supabase/schema.sql`.
2. Добавить `DATABASE_URL` и `DATABASE_API_SUPABSE` в env (локально —
   `.env.development.local`, в проде — переменные окружения хостинга).
3. Прогнать `npx tsc --noEmit`; запись проверяется живой сессией в боте
   (кнопка «Загрузить в систему» → строка в `materials`).

### Деплой на Railway

- `railway.json` в корне фиксирует сборку (`npm run build`) и запуск
  (`npm start` = долгоживущий `next start`, нужный для webhook-режима).
  Без него Railway тоже справится автоопределением, файл — страховка.
- Переменные окружения задаются в настройках сервиса Railway (не в файлах
  репозитория): `DATABASE_URL`, `DATABASE_API_SUPABSE`, плюс бот-переменные
  `TELEGRAM_BOT_TOKEN`, `BOT_MODE=webhook`, `TELEGRAM_WEBHOOK_SECRET`,
  `PUBLIC_BASE_URL`. Порт Railway подставляет сам — `env.ts` его читает.
- После первого деплоя один раз выполнить `npm run set-webhook`, чтобы
  Telegram знал адрес webhook.

## 9. Ограничения

- **Повторный /done после сбоя БД** прогоняет очистку заново — правила
  идемпотентны, результат тот же, дублирующей записи не будет (первая не
  записалась).
- **Нет ретраев записи.** Один попытка на финализацию; при сетевом сбое
  сессия сохраняется и повтор запускается вручную.
- **Таблица без ретеншена и индексов под основную систему** — схема
  минимальная под текущую задачу; выборки и нарезка чанков добавят свои.
